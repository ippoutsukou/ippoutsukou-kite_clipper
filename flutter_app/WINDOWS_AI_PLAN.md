# Windows版のAI解析（方式A：DartからONNX Runtimeを呼ぶ）

利用者の指示（2026-09-16）：Windows でも AI解析を使えるようにする。方式は A（既存Python実行ファイルの同梱ではなく、アプリ内で ONNX Runtime を呼ぶ）。

## 現状
- Android：実装済み（Kotlin → onnxruntime-android）。ビルド18で実機確認待ち。
- Windows：AI解析のみ未対応。ボタンを押すと「Android のみ対応」と表示する。
- 判定モデル（係数512個）・点数計算・移動平均・区間化・画面はDart側にあり、Windowsでもそのまま使える。
- PC実測：フレーム取り出し（FFmpeg・4K）約17秒/動画1分、CLIP推論 約40ms/枚。

## 方針
1. フレーム取り出しは既存の FFmpeg（vendor同梱）に任せ、**224×224のRGB生データ**をまとめて受け取る。
   前処理（短辺リサイズ→中央切り出し）もFFmpegの filter で行うため、Dart側の画像処理は不要。
2. CLIP推論のみを ONNX Runtime に任せる。Dart から呼べる形にするため、Windows側に薄い橋を1つ作る。
3. 点数計算（係数との内積＋シグモイド）、平滑化、区間化、進捗、中止、結果の保存は**既存のDartコードをそのまま使う**。
   進捗と中止はDart側のループで扱えるため、Androidより簡単になる。

## 橋の作り方（比較と決定）
- 案1：Dart FFI で DLL を直接開く。ONNX Runtime の C API は「関数ポインタの大きな構造体」を取得する形で、
  Dart側に構造体の並び順を正確に再現する必要がある。バージョンが変わると壊れやすい。→ 採用しない。
- 案2（採用）：Flutter の Windows 側（C++）に薄い処理を書き、メソッドチャンネルで Dart とやり取りする。
  Androidと同じ形になり、C API の扱いはC++側に閉じる。ONNX Runtime の公式ヘッダと .lib が必要。
  - チャンネル：`kite_clipper/analyze`（Androidと同名）。メソッド `embed`（224×224×3のバイト列 → 512個の数値）。
  - セッションは初回に作って使い回す。モデルは同梱ファイルから実行フォルダのパスで読む。

## 必要なダウンロード（承認待ち）
- ONNX Runtime 公式リリース（Windows x64、CPU版）の zip。
  - 取得元：GitHub の microsoft/onnxruntime リリースページ。
  - 含まれるもの：onnxruntime.dll、onnxruntime.lib、include/onnxruntime_c_api.h ほか。
  - サイズ：おおよそ 30〜60MB（実際の値は取得時に確認して報告する）。
  - ライセンス：MIT。同梱・再配布可。
  - 置き場所：`vendor/onnxruntime/windows-x64/`（vendor は Git 管理外）。
- 手元の `.venv` 内に onnxruntime 1.27.0 の DLL はあるが、ヘッダと .lib がないため C++ からは使えない。
  バージョンを揃えるため、DLLも公式zipのものを使う。

## タスク
1. ONNX Runtime（Windows）の取得と配置。内容・サイズ・ライセンスを報告。
2. FFmpeg から 224×224 RGB を取り出す Dart 側の処理（1秒ごと、まとめて取得、進捗と中止に対応）。
3. Windows の C++ 側に `embed` を実装（CMakeでリンク、DLLを実行フォルダへコピー）。
4. AnalysisService を Windows 対応にし、点数計算をDart側で行う（Androidは現状のまま）。
5. Windows で実測（4K動画1分あたりの秒数）し、Androidの結果と比較。
6. 利用者確認。

## 非対象
- Android 側の作り直し（現状維持）。
- 競技の自動判定、モデルの再学習。
- 配布用のパッケージ整理（CLIPモデル89MBの扱いを含む。配布を考える段階で別途）。

## 実装（Windows）
- windows/runner/clip_embedder.h / .cpp：チャンネル `kite_clipper/clip` のメソッド `embed`。
  224×224×3のRGBバイト列を受け取り、CLIPのmean/stdで正規化してONNX Runtimeに通し、
  L2正規化した512個の数値を返す。セッションは初回に作って使い回す。
  FlutterのWindowsビルドは例外を無効化（_HAS_EXCEPTIONS=0）しているため、例外を使うC++ APIではなく
  C API（onnxruntime_c_api.h）を使い、失敗は文字列で返す。
  モデルは実行ファイル隣の data/flutter_assets/assets/clip/vision_model_quantized.onnx を読む。
- windows/runner/CMakeLists.txt：ソース追加、include と onnxruntime.lib のリンク、
  ビルド後に onnxruntime.dll を実行フォルダへコピー。
- windows/runner/flutter_window.cpp：起動時に RegisterClipEmbedder を呼ぶ。
- lib/analysis_service.dart：`supported` に Windows を追加。Windowsでは
  FFmpeg（fps＝間隔、scale＋crop、rgb24、rawvideo）で224×224を連続取得し、150,528バイトごとに
  `embed` を呼び、既存の `SportModel.score` で採点する。進捗・中止はDart側のループで処理する。
  所要時間は全体と推論を実測し、取り出し時間は差分として記録する。

## Windows実測（利用者・2026-09-16）
- 動作確認：Windows版でAI解析が最後まで動作し、区間提案・「区間として追加」まで表示された。
  C++側のCLIP推論は機能している。
- 妥当性：同じ4K動画（20260704_163131.mp4・18秒）で、
  Windows の提案「00:00〜00:17・平均0.56」に対し Android は「00:00〜00:17・平均0.53」。
  ほぼ一致しており、前処理・推論・採点の実装が両OSで整合していることを示す。
  （完全一致しないのは、フレーム取り出し位置と縮小方法の差によるものと考えられる。）
- 速度：18枚で合計124.0秒（取り出し121.6秒／推論2.4秒）＝動画1分あたり約413.3秒。
  Android（1分あたり約20.8秒）の約20倍遅く、このままでは実用にならない。
- 推論は2.4秒/18枚＝約133ms/枚。PC単体実測（約40ms/枚）より遅いのは、
  UIスレッド実行とチャンネル往復のためと考えられる。まずは取り出しの改善が先。

## 遅さの原因（見立て）と対策の実測
- 原因：Windows実装は FFmpeg に `fps=1` を指定しており、これは全フレームをデコードしてから
  1秒ごとに1枚選ぶ動作。この動画は 4K・HEVC・60fps のため、18秒でも1080フレームを
  すべてソフトウェアデコードすることになる。
  Android は MediaMetadataRetriever が「指定時刻へシークしてその1枚だけ取り出す」方式のため速かった。
- 比較する方式：
  1. 現行（fps=1で全デコード）
  2. 1秒ごとに `-ss` で位置指定して1枚ずつ取り出す（既存のサムネイル取得と同じ考え方）
  3. GPUデコード（-hwaccel d3d11va）＋fps=1
- 実測中。最も速い方式に実装を差し替える。

## 取り出し方式の実測（4K HEVC 60fps・18秒・18枚）
| 方式 | 所要 | 備考 |
|---|---|---|
| 1. 現行（fps=1で全デコード） | 82.9秒 | アプリ内実測では121.6秒（他処理と競合） |
| 2. 位置指定(-ss)で1枚ずつ18回 | 25.5秒 | プロセス起動18回を含む |
| 3. GPUデコード(d3d11va)+fps=1 | 13.6秒 | 現行比で約6倍速 |
- 方式3でも動画1分あたり約45秒相当で、Android（約20.8秒）には届かない。
- 未測定の組み合わせ（位置指定＋GPU、キーフレームのみ＋GPU）を追加実測中。
- 追加実測：
  | 方式 | 所要 | 備考 |
  |---|---|---|
  | 4. 位置指定(-ss)＋GPU、1枚ずつ18回 | 13.3秒 | プロセス起動18回を含む。方式3とほぼ同等 |
  | 6. GPU+fps=1（方式3の再測） | 15.4秒 | ばらつき±1.8秒程度 |
  | 5. キーフレームのみ＋GPU | 測定不可 | `-vsync` は新しいFFmpegで廃止。`-fps_mode` で測り直す |
- 現時点の最速は方式3/4（13〜15秒＝動画1分あたり約45〜50秒）。Androidの約20.8秒には未達。
- 方式4はプロセス起動を18回行うため、長い動画（600枚など）では起動の積み上がりが不利。
  長尺では方式3（1プロセス）が有利で、短尺では方式4が有利という関係。

## 取り出し方式の決定（2026-09-16）
| 方式 | 所要（18〜19枚） | 動画1分あたり換算 |
|---|---|---|
| 現行（fps=1で全デコード） | 82.9秒 | 約276秒 |
| 位置指定(-ss)で1枚ずつ | 25.5秒 | 約85秒 |
| GPU(d3d11va)+fps=1 | 13.6〜15.4秒 | 約45〜51秒 |
| 位置指定＋GPU | 13.3秒 | 約44秒 |
| キーフレームのみ（CPU） | 1.84秒 | 約6秒 |
| キーフレームのみ（GPU） | 0.74秒 | 約2.5秒 |

- 対象動画のキーフレームは19個・間隔約0.95秒（0.000／0.950／1.900…）。解析の1秒間隔とほぼ一致する。
- 採用：**キーフレームのみ（`-skip_frame nokey -fps_mode passthrough`）、GPU指定なし**。
  CPUでもAndroid（約20.8秒）より速く、`-hwaccel` の環境依存トラブル（非対応GPU・ドライバ差）を避けられる。
- 時刻は ffprobe（`-skip_frame nokey -show_entries frame=pts_time`）で先に取得し、取り出した順番と対応させる。
  等間隔の仮定をやめ、実際のキーフレーム時刻を使う。
- 希望間隔（1秒/2秒）より細かいキーフレームは採点せず読み飛ばす。上限3600枚は維持。
- 注意：キーフレーム間隔は動画次第。間隔が粗い動画（数秒に1枚）では提案区間も粗くなる。
  結果画面の「解析したフレーム数」で判断できる。必要になれば間隔に応じた方式切替を検討する。

## キーフレーム間隔が粗い動画への対策（項目4・2026-09-16）
- 背景：キーフレーム間隔は動画で異なる（実測：GoPro 0.94秒、テスト用H.264 2.0秒、合成動画 1.33秒）。
  キーフレームが2個以上あっても間隔が粗い動画では、1秒を指定しても実際にはその間隔でしか採点できず、
  利用者が気づけないまま粒度が粗くなる。
- 対策1：`keyframesUsable(timesMs, intervalMs)` を追加。キーフレーム間隔の中央値が希望間隔の3倍を
  超える場合はキーフレーム方式を使わず、間隔指定（fps）方式へ切り替える。遅いが希望の粒度を保てる。
  中央値で判断するため、一部だけ間隔が空いている動画は影響を受けない。
- 対策2：結果画面に「実際の間隔：約○秒」を表示し、粒度を把握できるようにした
  （`AnalysisResult.averageIntervalMs`）。
- 判定処理は公開関数にして単体テストを追加（約1秒間隔・2秒間隔・5秒間隔・1枚のみ・空・不正な間隔・
  一部だけ空いている場合）。
- 検証：静的解析成功、テスト91件成功（-j 1。キーフレーム判定のテスト1件を追加）、Windowsビルド成功。
  利用者による確認待ち（修正版での当該動画の解析、5分以上の長い動画）。

## 速度改善：取り出しと採点の分離（項目1・2026-09-17）
- 課題：1枚読む→採点の完了を待つ→次を読む、という流れのため、採点中はFFmpegからの読み取りが止まる。
  パイプが詰まってFFmpeg側も待機し、枚数が増えるほど停止が積み上がる。
  実測の1枚あたり取り出し時間：FFmpeg単体0.10秒／17秒の動画0.27秒／6分の動画0.51〜0.88秒。
- 対処：`process.stdout.listen` で読み取りを続けながら、採点は別の流れで順に処理する。
  採点待ちが32枚を超えたら読み取りを一時停止し、16枚まで減ったら再開する（メモリは最大約4.7MB）。
- 期待：FFmpeg単体（0.10秒/枚）に近づけば、6分の動画で取り出し約37秒＋採点約23秒＝1分程度。
  現状は209.8〜352.4秒。
- 実測ばらつきの記録：同じ動画・同じ368枚で、kite_static実行時352.4秒／kite実行時209.8秒。
  ディスクキャッシュ等の影響と考えられるため、改善効果は複数回の実行で確認する。
