# AI候補の提案：本実装（ビルド18以降）

測定（ビルド17）で実用的な速度（4K実素材で動画1分あたり約20.8秒）を確認したため、測定用から本実装へ進む。
利用者の指示（2026-09-16）：下記1〜5を順に進める。決めた点は既定案で実装し、実機確認時に合わせて判断してもらう。

## 1. 提案区間を一覧に追加する
- 解析結果の画面に「区間として追加」を置く（提案が0個なら無効）。
- 追加の仕方：
  - その動画の区間が「触っていない初期状態（全体1区間・保存結果なし）」なら、提案で置き換える。
  - それ以外は既存の区間を残して後ろに追加する。
- 上限20区間。入りきらない分は追加せず「N個は上限のため追加していません」と表示。
- 追加後は最初に追加した区間を選び、その開始位置へ移動する。
- 追加した区間は普通の区間として扱う（範囲の変更・削除・保存・一括保存が可能）。
- 元動画・保存済みファイルには触れない。

## 2. 進捗表示と中止
- 解析中は「N / M 枚を解析中」と進捗バーを表示し、「中止」を置く。
- 中止は、いま処理中の1枚が終わってから止める。そこまでの結果で区間を提案する（部分結果として明示）。
- 進捗はネイティブ側から一定間隔（8枚ごと）で通知する。
- 解析中は追加・切替・区間操作・保存を無効化（既存の busy を使用）。

## 3. 解析結果を保存する
- 動画ごとに、解析に使った競技・フレーム間隔・動画の長さ・時刻と点数を作業記録（session.json）へ保存する。
- 同じ動画・同じ競技・同じ間隔・同じ長さなら、再解析せず保存した結果から区間を作る（「前回の結果を使用」と表示し、「解析し直す」も選べる）。
- 点数は小数3桁に丸めて保存する（1時間の動画で約90KB）。
- 動画の長さが変わっていた場合は保存結果を捨てて解析し直す。

## 4. フレーム数の上限
- 300フレームの打ち切りをやめ、動画全体を解析する。
- 暴走防止のため上限3600フレーム（1秒間隔で1時間）とし、超える場合は間隔を自動で広げる。

## 5. フレーム間隔の選択
- 解析開始時に1秒・2秒を選べるようにする（既定は競技モデルの値＝1秒）。
- 2秒にすると所要時間はおよそ半分、区間の切れ目は粗くなる旨を画面に表示する。

## 非対象（この段階ではやらない）
- 競技の自動判定、モデルの再学習、しきい値の画面からの調整。
- Windows版のAI解析（ONNX Runtime の同梱が別途必要）。
- 複数動画の一括解析。

## 検証方針
- 純Dart部分（追加の仕方、上限、保存形式、間隔の切り替え）は単体テストで確認する。
- 解析中の進捗・中止・実速度は実機（ビルド18）で利用者が確認する。

## 実装（ビルド18）
- clip_session.dart：`AnalysisRecord`（競技・間隔・長さ・時刻・点数・部分結果か）を追加し、`ClipItem.analysis` に保持。
  `isUntouchedDefault`（触っていない初期区間の判定）と `addSegmentRange`（範囲指定の追加）を追加。
- ai_segments.dart：`applyProposedSegments`。初期状態なら置き換え、そうでなければ後ろに追加。上限20を超える分は追加せず件数を返す。最初に追加した区間を選ぶ。
- session_store.dart：解析結果も作業記録へ保存・復元。点数は小数3桁。壊れていればその結果だけ捨てる。
- analysis_service.dart：進捗コールバック、中止、フレーム間隔の指定、上限3600枚に収める `resolveIntervalMs`。
- MainActivity.kt：進捗通知（8枚ごと）、中止（処理中の1枚の完了後に停止、部分結果を返す）、`cancelled` を返却。上限はDart側指定。
- analysis_dialogs.dart：開始（競技・間隔・保存済みの有無）、進捗（枚数・バー・中止）、結果（所要時間・提案一覧・「区間として追加」）。
- main.dart：保存済み結果の再利用、解析、進捗、中止、提案の反映、ボタン名を「AI解析」に変更。

## 実装時の判断
- 進捗表示は画面の状態ではなく通知オブジェクトで更新する（解析中の再描画を最小にするため）。
- 中止・打ち切りの結果は `partial` として保存し、再利用の対象にしない（次回は解析し直す）。
- 保存済み結果の判定には動画の長さも使う。長さが変わっていれば解析し直す。

  採用率比では kite 1.6倍・windsurf 1.2倍で、kite が特に劣るわけではない。
  根本的な精度向上は教師データの追加が必要で、しきい値調整では到達できない。

## 長い動画での実測（項目1の残り・完了／2026-09-16）
- GX014849.MP4（GoPro・6分08秒）を kite_static で解析。368枚・実際の間隔1.0秒。打ち切りなしで最後まで完了。
- 所要：合計352.4秒（取り出し325.2秒／推論27.2秒）＝**動画1分あたり約57.4秒**。
- 提案区間9個・合計約291秒（動画全体の約79%）。平均点は0.48〜0.61。

### 課題1：長い動画ほど1枚あたりが遅くなる
| | 1枚あたりの取り出し |
|---|---|
| FFmpeg単体（コマンドで実測） | 0.10秒 |
| アプリ・17秒の動画 | 0.27秒 |
| アプリ・6分の動画 | 0.88秒 |
- 原因（設計上の問題）：現在は「1枚読む→推論の完了を待つ→次を読む」を繰り返しており、
  推論中はFFmpegからの読み取りが止まる。パイプが詰まってFFmpeg側も待機するため、
  枚数が増えるほど停止の積み上がりで悪化する。
- 改善案：読み取りと推論を分離する（読み取りは止めずに続け、推論は別の流れで順に処理する）。
  FFmpeg単体の0.10秒/枚に近づけば、6分の動画で約37秒＋推論27秒＝1分程度まで短縮できる見込み。

### 課題2：提案が全体の79%を占め、絞り込みになっていない
- kite_static は「置き撮りで明らかに不要なフレームを捨てる」用途で作った道具であり、
  良い場面を選び出す用途には向いていない（学習時のしきい値0.5での適合率0.36）。
- 同じ動画を kite モデルでも解析し、提案数と内容を比較する必要がある。
- 改善案（前回の記録と合わせて）：解析時に全モデルで採点し、提案数を並べて示す。
  CLIP埋め込みは共通のため追加コストはほぼゼロ。

## 同じ長い動画を kite モデルで解析（2026-09-17）
- GX014849.MP4（6分08秒・368枚）を kite モデルで解析 → **提案区間0個**。
- 所要209.8秒（取り出し187.1秒／推論22.7秒）＝1分あたり34.2秒。
  同条件の kite_static 実行（352.4秒）と比べて大きく差があり、実行ごとのばらつきが大きい。
- 比較：kite_static は9区間（全体の79%）、kite は0個。**どちらも絞り込みとして機能していない**。
- 結論：しきい値やコードの問題ではなく、モデルと撮影スタイルの適合性の問題。
  この動画は置き撮りでカイトが遠く小さく写る映像で、kite（GoProの主観・追尾映像で学習）とは傾向が異なり、
  kite_static（不要フレームを捨てる用途）では全体が高得点になる。
- 根本策：この撮影スタイルの教師データを追加して学習し直す（Python側の既存手順で可能）。
  アプリ側の改修では解決しない。
