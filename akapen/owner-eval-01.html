今のAIは、オーナーが「使う場面」をほとんど見分けられない

結論: 今の kite 設定のおまかせは素材の6割（343秒）を残し、その中でオーナーが実際に使った部分は18%でした。でたらめに選んだ場合の14%とほぼ同じです。オーナーは見せ場があるときだけ短く撮るので、素材のほとんどにカイトが写っています。「カイトが写っているか」を見る今のモデルでは、使う場面と使わない場面の点数に差が出ません。次は、オーナーの採否そのものを学習したモデルが必要です。
このシートで使う言葉:
正解区間 — 完成動画の1コマずつを元素材から探して特定した「オーナーが実際に使った区間」
点数 — モデルが動画の1秒ごとに付ける0〜1の値。高いほど「残す場面」らしい
提案 — おまかせが点数をもとに動画へ自動で入れる区間
採否 — オーナーがその場面を完成動画に使ったか、使わなかったか
学習 — 正解つきの例を大量に見せて、モデルの点数の付け方を作ること
再現率 — 正解区間のうち、AIの提案に含まれた時間の割合（高いほど取りこぼしが少ない）
適合率 — AIの提案のうち、正解区間だった時間の割合（高いほどムダが少ない）
おまかせ — 動画を追加すると自動で AI解析し、区間を入れるアプリの機能。kite / wing / windsurf / kite_static は競技別のモデル名
enter / exit — 区間を始める点数と、続ける点数の下限（kite は 0.5 / 0.4）

使われた動画も使われなかった動画も、ほぼ丸ごと提案している

下の図は54本を1行ずつ並べたものです。赤枠がオーナーが使った区間、灰色の帯が kite の提案です。上の26本（使われた動画）でも下の24本（使われなかった動画）でも、灰色の帯の付き方はほとんど同じです。モデルの点数が、オーナーの採否と関係なく動いていることがわかります。

しきい値を変えても改善せず、単純なルールより成績が下

kite のしきい値を 0.6 に上げると提案が0個になり、0.4 以下にすると素材のほぼ全部が残ります（report.txt:15-17）。「各動画の先頭3秒だけ採る」という単純なルールのほうが、今の kite より成績が上でした。点数の高い順に正解と同じ82秒分を採ると、適合率は40%まで上がります。つまり点数の高い場面ほど当たりやすく、点数に手がかりはあります。ただしその方式では正解の74%を取りこぼします。

決めてほしいこと (3 問 — 未回答は推奨で進める)

問 1. オーナーの採否を学習するモデル作りを、いつ始めるか（開発側の進め方。オーナーのアプリの画面はこの問いでは変わらない）

  • A. 今の1セットで試しに作り、同時に別の撮影日の素材を依頼する推奨 — 利点: 待たずに効果の見込みがわかり、依頼文に結果を添えられる。代償: 例が使用26本・未使用24本しかなく、試しに作ったモデルで測る成績は実際より良く出やすい。
  • B. 別の撮影日の素材が届くまで始めない — 利点: 作るのに使う日と、成績を測る日を分けられ、成績を正直に測れる。代償: 素材が届くまで何も進まない。

根拠: 正解の例は dataset/owner/2026-10-07_10/eval/report.txt:1「正解区間 33個 / 81.6秒（26本）」。元素材のファイル名は 20261007_*（10本。図2では 261007_…）と 20261010_*（44本）の2日分だけ。

問 2. 新しいモデルができるまで、オーナーが使うおまかせの設定をどうするか

  • A. 変えない（kite 0.5/0.4 のまま）推奨 — 利点: 取りこぼしが少なく（再現率73%）、説明し直す必要がない。代償: 素材の6割（343秒）が残り、選別の手間はあまり減らない。
  • B. 「目標の長さに収まるまで点数の高い順に採る」方式を先に作る — おまかせの設定に「目標の長さ（例: 3分）」の入力欄を足し、点数の高い場面から順に区間を入れる。利点: 残る長さが目標に近くなり、ムダが少ない（適合率40%）。代償: 取りこぼしが多い（再現率26%）うえ、アプリの改修が要る。
  • C. おまかせを「各動画の先頭3秒を区間にする」ルールに切り替える — 利点: 残る長さが半分（159秒）になり、今の kite より取りこぼしも少ない（再現率55%・適合率29%）。代償: AIを使わない固定のルールで、長い動画やほかの利用者の撮り方には合わない。

根拠: 表 1（report.txt:6）。kite のしきい値は flutter_app/assets/models/kite.json:1（"enter": 0.5, "exit": 0.4）、区間の作り方は flutter_app/lib/ai_segments.dart:153（buildProposedSegments）。

問 3. オーナーに今回の結果をいつ伝えるか

  • A. 追加素材のお願いと一緒に、要点だけ今伝える推奨 — 利点: 「なぜ追加素材が要るか」が伝わり、協力を得やすい。代償: 「今のAIはあまり効いていない」と伝えることになる。
  • B. 改善できてから、結果と改善をまとめて伝える — 利点: 良い知らせと一緒に伝えられる。代償: 追加素材の依頼の理由を説明しにくく、届くのが遅れる。

根拠: オーナー宛ての依頼文の案は flutter_app/HIGHLIGHT_MODELS_PLAN.md:70 「## 4. オーナーへの依頼文（案）」。今回もらった素材はファイル名から 2026-10-07 と 2026-10-10 の2日分（dataset/owner/2026-10-07_10/raw の54本）。

正解区間の作り方と限界（照合の方法、正解から外した3か所、照合できなかった2か所）

完成動画を0.25秒ごとのコマにし、元素材の全コマ（0.25秒ごと）と SIFT 特徴点で照合しました。SIFT は拡大縮小に強いので、完成側のズーム・切り抜きにも対応できます。448コマ中422コマが一致し、そのうち55コマは水しぶき等で特徴点が少ないため、前後の区間から時刻を予測して補いました（owner_eval/match_final.py）。

正解から外した部分: 0〜11.75秒（タイトル文字の背景）、12〜19秒（写真＝静止画。動画ではないので今回は評価しないと決めた部分）、108.5秒以降（YouTube の終了画面）。照合できなかった部分: 31〜33秒（大きな水しぶきの転倒）、91〜92秒（空中でボードが回るジャンプ）。どちらも約1〜2秒で、正解の合計82秒への影響は小さいと見ています。

Flutter版の解析の実行方法と注意点（3項目）

評価専用の起動ファイル flutter_app/tool/eval_omakase.dart が、アプリのおまかせと同じ解析（FFmpeg＋Windows側のCLIP、1秒間隔）と区間作成を呼び、4モデル分の点数と提案を JSON に書き出します。54本の解析は約90秒でした。

Debug版の exe は、Defender のフォルダーアクセス制御のため Documents 配下に書き込めません。出力は Temp に書いてからコピーしています。評価用の起動ファイルで実行したため、build/windows/x64/runner/Debug の中身は評価用に置き換わっています。通常の flutter run をすると、アプリ本体に作り直されます。

「点数が高い順に82秒分」は、重なった区間の時間を二重に数えているため、実際に残るのは54秒です。目安として見てください。
